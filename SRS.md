### 0.2 Rules of interpretation

1. **MUST / SHOULD / COULD** follow RFC 2119 meaning. MUST = release blocker. SHOULD = expected unless an ADR justifies skipping. COULD = optional / later.
2. Every requirement has an ID (`FR-<MODULE>-<NN>`, `NFR-<AREA>-<NN>`, `SEC-<NN>`). Reports, tests and commits MUST reference IDs.
3. If this document is ambiguous or contradicts itself, Claude MUST NOT guess. Claude raises a question in the plan (Section 15 lists decisions already known to be open).
4. Deviation from this SRS is allowed only through a written **ADR** (Architecture Decision Record) approved by the Owner.
5. Claims in reports must be backed by **evidence** (test output, CI links, screenshots, commit hashes). Auditors verify evidence; they do not accept assertions.
6. Enterprise-level means: typed end to end, tested, observable, secure by default, documented, and reproducible from a clean checkout in one command.

## 1. Introduction

### 1.1 Problem
Freelancers who serve local B2C businesses (gyms, taxi operators, wedding/event planners, distributors, salons, clinics) repeatedly build near-identical small business websites: static or lightly dynamic, a few pages (Home, Services, Gallery, About, Contact), a contact form that emails the owner, and little else. Budgets are small, so the freelancer must deliver fast. Today they lose time on:

- writing the same code repeatedly,
- chasing clients for logos, photos, prices and phone numbers,
- managing hosting, DNS, SSL, email and source code separately for every client,
- showing work-in-progress safely, and handling endless small change requests after delivery.

### 1.2 Vision
A **freelancer-first, multi-tenant SaaS "operating system for local-business websites"**:

1. Freelancers browse **category-based premium templates** (free and paid), preview them to prospects, and once the client approves, customise the template through **structured editing and prompt-based AI** – without hand-coding.
2. The platform **collects client data through a magic-link onboarding wizard**, hosts and manages each client site separately, connects custom domains, captures leads, and supports **white-labeling**.
3. Freelancers can **export source code** or push it to their own GitHub/Vercel, so there is no lock-in.
4. Freelancers with no current client can **create and sell templates** on a marketplace that other freelancers use, creating a two-sided economy.

### 1.3 Scope

**In scope (v1):** everything in Sections 6–9 and phases P0–P8.

**Out of scope (v1)** – recorded so nobody builds them by accident:

- Full e-commerce / shopping cart / inventory (contact-and-booking-enquiry only).
- Freelancer-to-client invoicing and payment collection (the "Approve & Pay" idea is deferred; v1 records client *approval* only, not money).
- Arbitrary custom-code components inside marketplace templates (see ADR-004 – declarative templates only in v1).
- Native mobile apps.
- Real-time multi-user co-editing (single-editor lock in v1).
- Domain *registration/purchase* inside the Platform (we connect domains that clients already own).

### 1.4 Definitions

| Term | Meaning |
|---|---|
| **Workspace** | A freelancer's or agency's account space. The unit of tenant isolation. (The earlier draft called this "Tenant". Code uses `workspace_id` as the isolation key.) |
| **Project** | One client's website inside a Workspace (e.g., "Sharma Taxi"). |
| **Template** | A reusable, declarative site definition (design tokens + page/section layout + onboarding manifest) built from platform-owned **Blocks**. |
| **Block** | A platform-owned, tested UI component (Hero, Services, Pricing, Gallery, Contact, …) with variants and a Zod-typed props schema. |
| **SiteDraft** | The mutable working configuration (JSON) for a Project. |
| **SiteVersion** | An **immutable** snapshot of a SiteDraft created on publish (staging or live). Rollback = pointing to an older SiteVersion. |
| **Client** | The local business owner. Not a freelancer. Access is via magic link or a limited portal login. |
| **Visitor** | Anonymous end-customer browsing a client's site. |
| **Creator** | A Workspace that publishes templates to the marketplace. |
| **AI Credit** | The platform's billing unit for AI usage, derived from model-weighted tokens (Section 8.4). |
| **ADR** | Architecture Decision Record. |

### 1.5 Personas

| Persona | Goal | Key needs |
|---|---|---|
| **Freelancer / Agency owner** (primary) | Deliver 5× more client sites, faster | Templates, easy customisation, client data collection, one place to manage all client sites |
| **Team member** | Help build/manage sites | Role-limited access |
| **Template Creator** | Earn money and recognition | Submission tooling, fast approval, analytics, payouts |
| **Client (local business owner)** | Get a good site and leads with minimal effort | Mobile-friendly onboarding, lead notifications, simple portal |
| **Visitor** | Find the business, call/WhatsApp/enquire | Fast, accessible, mobile-first site |
| **Platform Admin / Support** | Keep the platform safe and healthy | Moderation, tenant management, audit, cost visibility |

### 1.6 Competitive context
Wix, Squarespace, Framer, Webflow serve end users or designers, not freelancers managing dozens of tiny client sites with a template economy. Vercel's "Platforms Starter Kit" and script bundles give multi-tenant plumbing, but no prompt-driven structured customisation, onboarding portal, or creator marketplace. **Differentiators:** freelancer-centric workflow + structured AI editing + client onboarding + local SEO + marketplace + export-anytime. (Market claims should be re-verified by the Owner before investor/marketing use.)

## 2. Architecture Review Notes – Corrections to the Earlier Draft

The earlier SRS draft was a good start but had gaps and several risks. This section lists what changed and why. **Claude and the auditors must treat this section as authoritative over anything in the earlier draft.**

| # | Earlier draft | Problem | Resolution in this SRS |
|---|---|---|---|
| C1 | `User` holds `monthly_token_balance`; `Tenant` has one `user_id` owner | Conflates person and account. Teams, multiple workspaces, ownership transfer become impossible. Credits belong to the paying account. | `User` ↔ `Membership` ↔ `Workspace`. Credits, plan and billing live on `Workspace`. |
| C2 | RLS "on tenant_id" but `Lead` only has `project_id` | RLS policies need the isolation key on the row itself; joins in policies are slow and error-prone. | Every tenant-owned table carries a denormalised `workspace_id` (enforced by composite FKs). |
| C3 | RLS with Prisma stated as a given | Prisma has no native RLS support. Naïve use leaks the tenant context across pooled connections. | Mandatory pattern in Section 5.3 (per-transaction `set_config`, non-bypass DB role, `FORCE RLS`, automated isolation test suite). |
| C4 | "Templates decoupled from code" **and** "freelancers download source" **and** "fork a repo per project" | Three incompatible deployment models. | Single primary model: **shared renderer + immutable SiteVersion snapshots** (platform-hosted). **Export** is a generated artifact (Section 6.14). Repo-per-project only happens at export/push time. |
| C5 | Creators "develop" templates but templates have "no raw React code" | Undefined what a creator actually submits. Allowing arbitrary code would let strangers run JS on shared origins. | ADR-004: v1 templates are **declarative** (tokens + layout + block variants + onboarding manifest). Custom components are a later, sandboxed phase. |
| C6 | AI returns the *entire* JSON | Costly, slow, higher drift risk, overwrites unrelated edits. | AI returns a **typed patch (operations)**, validated, previewed as a diff, then accepted by the user (Section 8.2). |
| C7 | Token ledger deducts after the fact from a "balance" | Concurrent requests can overspend; raw tokens hide the 5–10× price gap between models. | Append-only credit ledger with **reserve → commit/refund**, model-weighted credits, idempotency keys. |
| C8 | Model named "Claude 3.5 Sonnet" | Outdated. | Model IDs are **configuration, never hard-coded**. Defaults: heavy = `claude-sonnet-5`, light = `claude-haiku-4-5` (verify in P0). |
| C9 | Pinecone for RAG | Extra vendor, no RLS, overkill (each site's corpus is a few KB). | `pgvector` in the same PostgreSQL (RLS applies). Pinecone only if an ADR proves a need. |
| C10 | "Basic Next.js background routes or Inngest" | Serverless timeouts kill long jobs. | Durable job runner (**Inngest** recommended) with retries, idempotency and step functions. |
| C11 | Cloudflare for SaaS *and* Vercel both named for domains | If the sites app is on Vercel, proxying Vercel behind Cloudflare has known caveats. | `DomainProvider` interface + ADR-005. A spike in P0 decides the default. |
| C12 | Roadmap missing | No **billing/plans/entitlements**, **staging & review**, **GitHub/Vercel integration & source export**, **client portal**, **audit log**, **admin console**, **abuse controls**, **observability**, **backup/DR**, **privacy compliance**. | All added as modules and phases. |
| C13 | Marketplace in Phase 4, before billing exists | Paid templates need payments and entitlements first. | Marketplace + billing are one phase (P6), after client operations. |
| C14 | Dashboard and customer sites on the same origin | One XSS or cookie bug affects everyone. | Separate apps and **separate registrable domains** for the dashboard and tenant sites (ADR-002). |
| C15 | Stripe Connect assumed for payouts | Stripe Connect payout availability/onboarding for Indian creators can be limited; target users are largely Indian. | `PaymentProvider` interface; P0 spike compares Stripe Connect vs Razorpay (Route/Payouts). Owner decides (Section 15). |

### 2.1 Architect Review – Round 1 Disposition (Gemini → SRS v1.1)

Every finding was checked on its technical merit rather than accepted automatically. Where a finding was accepted only in part, or rejected, the reason is recorded so the auditors can challenge it.

| Ref | Finding | Disposition | What changed / why |
|---|---|---|---|
| F-01 | Paid-template IP leaks through source export | **Accepted, modified** | Export rights must follow the **licence type, not the export format**. Static HTML export of a paid template exposes the design just as much as a Next.js export, so gating only one of them is inconsistent. See FR-MKT-11/12, FR-EXP-01/06, D13. |
| F-02 | Prisma cannot pin a connection in `$transaction`; require Session-mode pooler or Neon HTTP driver | **Not accepted as written** | Prisma's interactive `$transaction` *does* hold one connection for the whole callback, which is exactly why transaction-local `set_config(…, true)` works behind a **transaction-mode** pooler. Session-mode poolers exhaust connections on serverless, and Neon's HTTP driver supports only batched (non-interactive) transactions. Section 5.3 now lists the real constraints; Spike B must prove the behaviour on the actual pooler with a negative leak test. If the spike disproves this, the SRS is revised. **Update: Spike B (Phase 0) confirmed our position** (one backend PID and the tenant setting persisted for a whole interactive transaction through transaction-mode PgBouncer; 400 concurrent operations, 0 leaks) – see `docs/spikes/SPIKE_B_RLS_POOLING.md`. |
| F-03 | Vercel + Cloudflare for SaaS "double proxy" | **Accepted** | ADR-005 is now a hard either/or rule. Exact vendor behaviour (IP blocking, limits, cost) is verified in Spike A, not assumed. |
| F-04 | GoDaddy API restricted | **Accepted** | FR-DOM-10 removed. Manual DNS + Domain Connect only. (Domain Connect still needs our DNS template onboarded with each provider – lead time planned in P0.) |
| F-05 | Image optimisation cost | **Accepted, modified** | Next.js/Vercel optimizer disabled; R2 + fixed pre-generated variants and/or Cloudflare transformations. Fixed presets keep cost predictable (per-transformation billing is otherwise open-ended). FR-BLD-05, ADR-009, Spike E. |
| M-1 | WAF/DDoS missing | **Accepted, modified** | SEC-19 added. Geo-blocking is an **optional per-project** setting, not a default: local businesses have legitimate visitors abroad (NRIs, destination weddings). |
| M-2 | No purge job for soft-deleted data | **Accepted, modified** | `retention.sweep` job (Section 8.7) + SEC-20. Audit and financial records follow their legal retention schedule (anonymise, not erase). |
| M-3 | Mandate Mumbai region | **Accepted, modified** | ADR-013 / SEC-21 / D14. Recommended for latency and customer trust. DPDP does not by itself require in-country storage (counsel to confirm), and the provider must actually offer the region. |
| Ph-7 | Phase 7 too large | **Accepted** | Split into **P7A** (Domains & White-Label) and **P7B** (Integrations & Export). Note: export is packaging renderer + config, not AST compilation. |
| D-series | Decision recommendations | **Accepted**, with edits | D3 Better Auth, D6 14-day payout hold, D7 no unlimited AI (already credit-based). D12 corrected: controller/processor chain is *client business → freelancer → platform* (SEC-15). D10 revised by D13. |

## 4. System Architecture

### 4.1 Context

```
                         ┌──────────────────────────── Platform ────────────────────────────┐
 Freelancer ──────────►  │  apps/dashboard  (builder, projects, marketplace, billing, admin)│
 Template Creator ─────► │        │  tRPC/Server Actions        ▲                           │
 Client (magic link) ──► │        ▼                             │ events                    │
 Platform Admin ───────► │  packages/db (Prisma+RLS) ── Postgres (Supabase, pgvector)       │
                         │        │                             │                           │
                         │        ▼                             │                           │
                         │  packages/jobs (Inngest) ── AI / SEO / email / domain / export   │
                         │        │                                                          │
 Visitor ──► CDN/Edge ─► │  apps/sites  (host→site resolve, render published SiteVersion)   │
                         └──────────────┬────────────────────────┬──────────────────────────┘
                                        │                        │
   External: Anthropic API · Upstash Redis · R2/S3 · Vercel/Cloudflare (domains/SSL) ·
             GitHub App · Vercel Integration · Stripe/Razorpay · Resend/SMTP ·
             WhatsApp Cloud API / SMS · Turnstile/hCaptcha · Sentry/OTel
```

### 4.2 Tenancy model (three levels)

1. **Platform** – global data (templates in marketplace, plans, admin).
2. **Workspace** – freelancer/agency; **hard isolation boundary** (RLS key).
3. **Project** – one client's site inside a workspace; secondary boundary (leads, drafts, versions, client access).

### 4.3 Request flows

**Visitor request (hot path – must be fast and cacheable)**
1. Request reaches CDN/edge with `Host: sharmataxi.com`.
2. Middleware in `apps/sites` resolves `host → {site_id, published_version_id}` from Upstash Redis (REST, edge-compatible). Cache miss → a narrow, read-only DB function (`resolve_host`) → write back with TTL.
3. Renderer loads the **immutable SiteVersion JSON** (cached by version id; never changes, so cache forever) and renders server-side with SEO tags and JSON-LD.
4. Publishing/rollback/domain change **invalidates** the host key and cache tags.

**Dashboard request**
1. Session → user → active `workspace_id` (from membership, never from client-supplied input alone).
2. Data-access layer opens a transaction, sets `app.workspace_id` (Section 5.3), executes queries.
3. Every mutation writes an `AuditLog` entry.

**Lead submission (public write path)**
Visitor form → `POST /api/public/leads` on the sites app with site key → bot check + rate limit → SECURITY DEFINER DB function inserts the lead with the correct `workspace_id` → job fan-out (notify owner, AI triage) → 202.

### 4.4 Recommended repository layout (Claude may propose changes via ADR)

```
/apps
  /dashboard        # freelancer/creator/admin/client-portal UI (Next.js App Router)
  /sites            # tenant site renderer + public APIs (Next.js App Router)
/packages
  /db               # Prisma schema, migrations, RLS SQL, tenant-scoped client, seed
  /schema           # Zod schemas: SiteConfig, Template, Patch ops, API contracts
  /blocks           # renderer Blocks (React), variants, motion presets, block registry
  /ai               # prompts, model router, patch generation, evals, credit ledger
  /jobs             # Inngest functions (SEO, triage, embeddings, domains, export)
  /providers        # DomainProvider, PaymentProvider, EmailProvider, StorageProvider, WhatsAppProvider
  /ui               # shared design system (shadcn/ui based)
  /config           # eslint, tsconfig, tailwind presets
```

### 5.3 Multi-tenant isolation (mandatory pattern – SEC-01…SEC-06)

1. **Two DB roles:** `migrator` (owns tables, runs migrations) and `app_user` (`NOSUPERUSER NOBYPASSRLS`, used by the app). A third narrow role `app_public` is used only by public/visitor paths and can execute specific `SECURITY DEFINER` functions (`resolve_host`, `get_published_version`, `insert_lead`) and nothing else (no table privileges). **No role needs SUPERUSER or BYPASSRLS** (managed Postgres does not provide them): the definer functions are owned by a NOLOGIN, NOBYPASSRLS role `svc_definer` that receives explicit, narrow RLS policies (e.g., `FOR SELECT TO svc_definer USING (true)` on `domain`), each visible in `pg_policies`. `migrator` is made a member of `svc_definer` **`WITH INHERIT FALSE, SET TRUE`** – with the default INHERIT it would inherit those policies and could read every tenant's rows (found in Spike B). Transferring function ownership needs the new owner to hold `CREATE` on the schema for that statement only; `INSERT … RETURNING` needs a column-level `SELECT`.
2. Every tenant table: `ALTER TABLE … ENABLE ROW LEVEL SECURITY; ALTER TABLE … FORCE ROW LEVEL SECURITY;` with policies of the form `USING (workspace_id = current_workspace()) WITH CHECK (workspace_id = current_workspace())`, where `current_workspace()` is `NULLIF(current_setting('app.workspace_id', true), '')::uuid`. **The `NULLIF` is mandatory:** the bare form `current_setting('app.workspace_id', true)::uuid` raises `22P02 invalid input syntax for type uuid: ""` on any pooled connection that has previously run a transaction-local `set_config` (Spike B: 20 of 20 attempts). Missing/empty setting ⇒ zero rows (fail closed).
3. **Prisma pattern:** a Prisma client extension wraps each request's queries in `$transaction`, first executing `SELECT set_config('app.workspace_id', $1, true)` (transaction-local). Never use session-level `SET` (it leaks across pooled connections). Prisma's interactive `$transaction` pins one connection for the whole callback, so a transaction-local `set_config(…, true)` is safe behind a pooler in **transaction mode** (with the flags Prisma requires for it, e.g., `pgbouncer=true`). Two supported forms, both proven in Spike B: the client extension (`$allModels.$allOperations`, executed as a batch transaction) and an explicit interactive `withWorkspace(id, fn)` transaction; **prefer one request-scoped `withWorkspace` per request** – the per-query wrapper adds round trips (local p50 8.05 ms vs 2.48 ms). Constraints: (a) every tenant query MUST go through the wrapper – a query outside it has no context and returns zero rows (fail-closed, and caught by the isolation suite); (b) keep transactions short (they pin a connection and have a timeout), set Prisma `transactionOptions` (`maxWait`, `timeout`) and the client pool size explicitly, and bound concurrency in the data-access layer – with Prisma defaults a 300-wide burst failed 156/300 requests with "Unable to start a transaction in the given time" (Spike B); (c) do not use the Neon HTTP driver for tenant queries that need interactive transactions (it supports batched transactions only); (d) Spike B must prove no context leakage under concurrent load against the real pooler, including a negative test that deliberately uses a session-level `SET` and shows the leak the suite must catch.
4. **Composite foreign keys** `(workspace_id, project_id)` so a row can never point to another workspace's parent.
5. **Cross-tenant test suite (release blocker):** auto-discovers every table having `workspace_id` and, for each, proves workspace A cannot SELECT/INSERT/UPDATE/DELETE workspace B's rows, including via joins, `RETURNING`, and raw queries. It also proves `app_user` cannot bypass RLS and that a query with **no** context returns zero rows. Runs in CI on every PR.
6. Object storage keys are prefixed `ws/<workspace_id>/…`; signed URLs are short-lived and issued only after an authorisation check.
7. Cache keys (Redis) are namespaced by workspace/site; never cache tenant data under a shared key.

## 8. AI Subsystem Specification

### 8.1 Principles
1. AI **proposes**; deterministic code **validates and applies**. The LLM never writes to the database or calls side-effecting tools.
2. Structured output only; nothing free-form reaches the renderer.
3. Human-in-the-loop for anything public-facing (diff preview → accept).
4. Cost is a first-class concern: measured per job, capped per plan, visible to admin.
5. All prompts, schemas, and eval sets are versioned in `packages/ai`.

### 8.2 Prompt-to-Patch pipeline

```
User prompt ─► entitlement + rate limit + credit RESERVE
            ─► context builder (compact view of SiteDraft, block registry summary, category/city/tone/language)
            ─► model router (heavy for creative multi-section; light for small edits)
            ─► generate structured PatchOperation[] (Zod, Vercel AI SDK)
            ─► validate: (1) op-level schema, (2) apply to a COPY of SiteDraft, (3) full SiteConfig validation, (4) safety rules (URLs, sizes, allowed fonts)
                  ├─ fail ► repair prompt with validator errors (≤ 2 retries) ► else fail gracefully, refund reserve
            ─► store ChangeSet(status=proposed) + diff
            ─► UI shows diff/preview ─► Accept ► apply to SiteDraft (new revision, undoable)
            ─► COMMIT credits from actual usage (input/output/cached tokens)
```

**Operations (closed set):** `setThemeToken`, `setBusinessField`, `updateBlockProps`, `setBlockVariant`, `addBlock`, `removeBlock`, `reorderBlocks`, `toggleBlock`, `setPageSeo`, `addPage`, `removePage`, plus `noChange {reason}` – a harmless escape hatch so a request that refers to something that does not exist, or cannot be done safely, yields a valid "nothing to do" answer instead of a hallucinated edit. Each has bounded arguments and targets nodes by stable `id`. **Implementation note (AI SDK v7):** structured output is `generateText` with `output: Output.object({ schema })` (`generateObject` is deprecated); the system prompt goes in `instructions`, not in `messages`.

### 8.3 Model routing (defaults, configurable)
| Task | Model tier | Notes |
|---|---|---|
| Whole-site copy, multi-section restyle, complex prompts | Heavy (default `claude-sonnet-5`) | Prompt caching on the static system prompt (schemas, block catalogue) |
| SEO tags, alt text, classification, lead triage, extraction, chatbot | Light (default `claude-haiku-4-5`) | High volume, low cost |
| Logo colours | Deterministic first; light vision model fallback | |
Verify model IDs, pricing and rate limits against current Anthropic documentation in P0 and store them in config with a "model registry" table (id, tier, cost per Mtok in/out/cached).

### 8.4 Credits, Ledger, Rate limiting, Fairness
- **Credit** = `(input_tokens × w_in(model) + output_tokens × w_out(model) + cached_tokens × w_cache(model))`, weights derived from real cost so cheap and expensive models are billed fairly. Store raw tokens **and** estimated cost (micro-currency) for margin analysis.
- **Reserve → Commit/Refund:** before a call, reserve the estimated maximum; after the response, commit actual usage and release the remainder; on failure refund. Prevents concurrent overspend. All ledger writes idempotent (`idempotency_key`) and transactional. Balance = sum of ledger (cached counter reconciled by a nightly job).
- **Plan grants** monthly (with expiry rules per plan) plus purchasable top-ups.
- **Limits (Upstash, token bucket):** per user (default 5 AI requests/min, configurable per plan), per workspace concurrency (e.g., 3 simultaneous jobs), and a **global** limiter + queue tuned below the Anthropic organisation limits. On upstream 429/5xx: exponential backoff with jitter, circuit breaker, and a user-friendly retry message.
- **Fairness under load:** weighted fair queue per workspace so one heavy user cannot starve others.
- **Failure policy:** failed/invalid generations are not billed to the customer.

### 8.5 Security of AI paths
- Treat **all** inputs as untrusted: freelancer prompts, client onboarding text, scraped/uploaded content, and chatbot visitor messages (prompt-injection). Untrusted text is delimited and labelled as data; system prompt states it must never be followed as instruction.
- LLM output has no side effects until validated and accepted.
- Chatbot: answers strictly from retrieved chunks of that site's published content; no tools; length-limited; refuses off-topic; per-IP/per-site rate limit; monthly conversation cap per plan; PII not logged beyond retention policy.
- Never place API keys in client code; server-only. Redact secrets/PII from logs and prompts.
- Log prompt/response metadata (not necessarily full content) for debugging with retention limits.

### 8.6 AI quality gates (evals)
- Golden prompt set per category (≥ 30 prompts/category by launch, incl. English, Hindi, Hinglish, adversarial/injection cases).
- Metrics tracked per release: **schema-valid-first-try rate**, **valid-after-repair rate** (target ≥ 99%), average tokens/job, p95 latency, "accepted-by-user" rate, cost/job.
- Any prompt or model change must pass the eval suite in CI before merge.

### 8.7 Event-driven automations (Inngest)
| Event | Jobs |
|---|---|
| `site.published` | generate/refresh SEO + JSON-LD, sitemap, embeddings for chatbot, cache invalidation, preflight snapshot |
| `asset.uploaded` | scan, re-encode, colour extraction, alt-text suggestion |
| `lead.created` | spam score, AI triage, notify owner, webhook fan-out |
| `onboarding.submitted` | build ChangeSet, notify freelancer |
| `domain.added` / `domain.check` | DNS pre-check loop with backoff, cert status polling |
| `template.submitted` | vetting pipeline |
| `export.requested` | build, smoke-test, package, notify |
| `billing.*` | entitlement sync, dunning, credit grants |
| `retention.sweep` (scheduled daily) | hard-delete expired soft-deleted rows/objects/vectors, expire onboarding tokens and staging links, purge leads past retention, reconcile the AI ledger |
All jobs: idempotent, retried with backoff, dead-letter queue with alerting, and traced with `workspace_id`.

## 11. Quality Assurance & Engineering Standards

### 11.1 Test pyramid (each phase must show the numbers in its report)
- **Unit:** schema validators, patch application, credit math, entitlements, permission matrix.
- **Integration:** DB with RLS (real Postgres in CI, not mocks), job handlers, provider adapters (with recorded fixtures/sandbox accounts).
- **Isolation suite:** Section 5.3 – mandatory.
- **Contract tests:** Zod schemas ↔ renderer ↔ AI outputs (fuzz/property-based tests: any valid config renders; invalid configs are rejected, never crash).
- **E2E (Playwright):** the phase's audit-checkpoint scenario, in CI.
- **Visual regression** for Blocks/templates (Playwright screenshots or Chromatic).
- **Performance:** Lighthouse CI on reference templates; k6 load test on the public site path and AI queue.
- **Accessibility:** axe in CI.
- **AI evals:** Section 8.6.
- **Security:** SAST (CodeQL/semgrep), dependency scan, secret scan, DAST baseline (ZAP) before launch.

### 11.2 Engineering workflow
- Trunk-based with short-lived branches, PRs required, CI green required (lint, typecheck, unit, integration, isolation, build).
- Conventional commits; each commit/PR references requirement IDs.
- Database migrations are forward-only, reviewed, and tested against a copy of seed data; RLS changes require a matching isolation test.
- Feature flags for incomplete features; environments: local, preview-per-PR, staging, production.
- Documentation as code: ADRs, runbooks, API docs (OpenAPI/tRPC docs), `CONTRIBUTING.md`, `SECURITY.md`.

### 11.3 Definition of Done (per requirement)
Implemented → typed → validated → authorised → audited (if sensitive) → tested (unit + relevant integration/E2E) → observable (logs/metrics) → documented → accessible → reviewed → demo-able.

- White-label: BrandProfile, portal domain, branded portal/wizard/emails, SMTP/domain-authenticated sending (SPF/DKIM/DMARC checks), badge removal (entitlement).
- Encrypted credential vault with key rotation (used by SMTP now, GitHub/Vercel/WhatsApp tokens later).
**Acceptance (Audit checkpoint):** a custom domain (real domain in test) is connected with correct DNS → ownership verified → SSL active → serves an AI-generated site under the freelancer's white-labeled brand, with the client portal on `portal.agency.com`; wrong or missing DNS never triggers repeated certificate requests; removing the domain removes provider configuration.
**Audit checklist:** takeover prevention, dangling-DNS cleanup, credential encryption/rotation, cache invalidation correctness, white-label leak audit (no platform branding in gated surfaces), email authentication results.

### Phase 7B – Integrations & Source Export (Size L)
**Scope:** INT, EXP (incl. licence gating per FR-MKT-11/12).
**Deliverables**
- GitHub App and Vercel integration (least-privilege scopes).
- Export pipeline (standalone Next.js + static HTML), async smoke-build before download, licence manifest, push-to-GitHub, deploy-to-Vercel; project-content export (FR-EXP-06).
- Server-side licence enforcement at export time, with tests that a paid non-exportable template can never be exported in any format.
**Acceptance (Audit checkpoint):** an eligible project (free/own/exportable-licence template) exports, builds and deploys to the freelancer's Vercel with identical rendering (visual diff) and contains no other tenant's data; a project on a non-exportable paid template is refused by every export path (UI, API, GitHub push) while content export still works.
**Audit checklist:** least-privilege GitHub/Vercel scopes and token storage, export reproducibility, licence enforcement bypass attempts, cross-tenant data in export artifacts, no secrets in exports.

### Phase 8 – Hardening, Compliance & Launch (Size L)
**Scope:** ADM full, ABU full, SEC-15/18, NFR verification, docs, beta.
**Deliverables**
- Full admin console (support impersonation with consent, takedowns, feature flags, cost/margin views).
- Load/soak tests vs NFR-SCALE-01; noisy-neighbour test; DR/restore drill; chaos tests on jobs/providers.
- External penetration test + remediation; DAST baseline; dependency/SBOM report.
- Compliance pack: privacy policy/ToS templates, DPA chain (client → freelancer → platform), `retention.sweep` job verified end to end (SEC-20), subject-access tooling.
- Runbooks/on-call, status page, alert routing, user documentation and onboarding tours, marketing-site handoff, private beta with feedback loop.
**Acceptance:** all NFR targets evidenced; zero open S1/S2 findings; restore drill passed; beta cohort completes the full journey (template → client → domain → lead) unaided.
**Audit checklist:** every MUST requirement traced to tests; pen-test report closure; DR evidence; cost model validated with real usage; go/no-go checklist.

## 13. Phase Report & Audit Protocol

### 13.1 Phase Report template (`docs/reports/PHASE_N_REPORT.md`) – Claude must fill **all** sections
1. **Summary** – what was built, in plain language (≤ 1 page).
2. **Scope traceability** – table: requirement ID → status (Done / Partial / Deferred / Dropped) → evidence link (PR, test, screenshot).
3. **Deviations** – any departure from the SRS with ADR links and rationale.
4. **Architecture snapshot** – diagrams/changes since the last phase; schema/migration list; RLS policy list (new/changed).
5. **Test evidence** – unit/integration/E2E/isolation/perf/a11y/AI-eval results with numbers and CI run links; coverage figures.
6. **Security self-review** – checklist against Section 9, threats considered, new attack surface, secrets handling, dependency scan output.
7. **Performance & cost** – measured metrics vs NFR targets; AI/infra cost observations.
8. **Demo script** – exact steps and seed accounts so the auditor can reproduce the acceptance scenario.
9. **Known issues & tech debt** – each with severity and plan.
10. **Risks & assumptions** – updated risk register.
11. **Readiness for next phase** – dependencies, open questions for the Owner.
12. **Repro instructions** – commit hash, how to run, environment variables required (names only).

### 13.2 Severity scale
| Level | Meaning | Gate rule |
|---|---|---|
| S1 Critical | Data leak, security hole, data loss, money error | Must be zero to pass |
| S2 Major | Requirement (MUST) not met or badly degraded | Must be zero to pass |
| S3 Moderate | SHOULD not met, notable UX/perf gap | Allowed with dated fix plan |
| S4 Minor | Polish | Backlog |

### 13.3 Verdicts
- **APPROVED** – proceed.
- **APPROVED WITH CONDITIONS** – proceed only after listed S3 items are scheduled and any listed prerequisites are closed.
- **REJECTED** – rework listed S1/S2 items; re-submit an updated report.

### 13.4 Auditor guidance (for ChatGPT and the Architect)
- Audit from the report **and the repository**; do not trust the narrative alone. Verify at least: the isolation suite result, three randomly chosen requirement→evidence links, one dependency/secret scan, one E2E run.
- Use a fixed scorecard: Correctness, Security, Tenant isolation, Test quality, Performance, UX, Maintainability, Documentation, Cost awareness (each 1–5 with comments), then verdict.
- Independence: the Architect and ChatGPT audit separately; the Owner reconciles differences. Disagreements on S1/S2 are resolved in favour of the stricter finding until disproved with evidence.
