# Phase 3, slice S7b: version history, diff, side-by-side preview and rollback

**Status:** built on `feat/p3-s7b-history-rollback` (commits `e842f04`, `2594655`, this report); CI-equivalent green (section 6); **approved by the Owner 2026-11-16**. **Date:** 2026-11-16 · **Requirement:** FR-PUB-03 (version history with author, note, timestamp, visual/JSON diff, one-click rollback to any live version) · **ADRs:** 002, 004, 005 · **Module:** 06 · **Plan approved by the Owner 2026-11-16** with the three decisions as recommended (section 3). **No migration:** nothing to apply to the live database.

## 1. Why

S7a made every publish an immutable version. S7b lets a freelancer use those versions: see who published what and when, see exactly what changed between two of them, put an earlier version back on Live in one click when a publish went wrong, and bring an old version back into the editor to keep working from it.

## 2. What was built

**Service** (`packages/workspaces`), each call one RLS transaction, authorized by capability, audited where it writes:

| Call                                  | Who                  | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `publishing.history`                  | any member           | Versions newest first, 20 per page; cursor = id of the last version shown (UUID v7 as tie-breaker, so pages are stable); filter all / live / staging; number, kind, author name, note, time; which version is on Live and on Staging now                                                                                                                                                                                                                 |
| `publishing.compare`                  | any member           | The structured diff of two versions of one project (`version-diff.ts`, below)                                                                                                                                                                                                                                                                                                                                                                            |
| `publishing.getVersion`               | any member           | One stored version with its content and image snapshot, for the side-by-side preview. A deleted project's versions are not shown                                                                                                                                                                                                                                                                                                                         |
| `publishing.rollback`                 | owner, admin         | Moves the Live pointer to an earlier **live** version. The browser sends the live version it showed: if Live moved since, `LIVE_CHANGED`. A retry after success finds Live already on the target and changes nothing (no second audit row). The live pointer row is locked `FOR UPDATE`. The target must still be a valid SiteConfig; no preflight (decision below). Audit `site.rolled_back` (from/to numbers), outbox `sites.hosts.changed.v1`         |
| `builder.restoreVersion` (decision 1) | owner, admin, editor | Puts any stored version (live or staging) into the draft as **one change set**: operation `restoreVersion` (id and number only), inverse `restoreConfig` (the whole previous draft), so Undo and Redo work as for any edit. Needs the edit lock, the expected revision and a change id (a retry returns the same revision; the same id with another version is `IDEMPOTENCY_MISMATCH`). Audit `draft.version_restored`. Live and Staging are not touched |

New error codes: `LIVE_CHANGED`, `ROLLBACK_TARGET` (a staging version cannot be rolled back to; publish it instead, so preflight runs), `VERSION_UNREADABLE`.

**Diff** (`packages/workspaces/src/version-diff.ts`, `diffConfigs`): a pure function, structured by what a freelancer recognises rather than JSON paths:

- business details, theme, menu, footer, integrations: field by field ("Business details > Phone", "Theme > Colors > Primary");
- pages: added, removed, moved, and title, address and search fields changed;
- sections (matched by id across the whole site): added, removed, moved (within a page or to another page), hidden, shown again, layout changed, and each changed field ("Home > Services > Items 2 > Title"), style and motion included.

Values are short plain text: rich text flattened, images by their description, at most 80 characters. At most 200 entries, the rest counted.

**Dashboard:**

- **Version history page** `/w/<slug>/projects/<id>/history`, linked from the project page and the editor's Publish panel. Each row shows number, Live/Staging, "Now on Live/Staging", time (Asia/Kolkata), who, the note, and the actions: "Compare with Version N" (the previous one), "Compare with Live", "Restore into the editor", "Put back on Live" (live versions not on Live, owners/admins). A compare form picks any two versions on the page. "Older versions" pages back.
- **Comparison:** the list of changes (before struck through → after), "Show this page below" on page-level entries, and **both versions side by side** in sandboxed iframes (stacked on narrow screens).
- **Stored-version preview** `/version-preview/<slug>/<versionId>`: renders a stored version with the same renderer, policy and sandbox as the editor preview. The editor-preview rendering and its policy moved into `lib/preview-response.ts`, now shared by both routes. `next.config.ts` excludes exactly these two paths from the global `frame-ancestors 'none'`. Images come from the version's own snapshot, filtered to the asset origin.
- **Confirmations:** both actions ask once more ("Make version 2 the live website again? Live shows version 3 now. Your draft does not change…" / "Replace the editor's current draft with version 2? Undo in the editor brings the current draft back…"). Restore then opens the editor.
- Two new server actions (`rollbackAction`, `restoreVersionAction`), both registered with the IDOR harness. The restore action takes the edit lock for the call when nobody holds it and gives it back afterwards; someone else editing is `LOCK_REQUIRED`.

## 3. Decisions

Plan approved by the Owner 2026-11-16 ("haan / recommended"):

1. **"Restore into the draft" is part of S7b.** Rollback changes only Live; without restore, continuing from an old version would mean rebuilding it by hand.
2. **Rollback targets are live versions only** (SRS: "rollback to any live version"). A staging version goes live through "Publish to Live", so preflight runs.
3. **Rollback is audited, not notified** for now. The notification event comes with module 09's publishing events. Recorded in DG-36.

Design choices inside the approved plan:

- **No migration.** The S1 `publisher_update` policy (owners/admins for live) and the pointer guard trigger (a live pointer only accepts a live version of its own project) already enforce rollback in the database.
- **Idempotency without a new column:** rollback compares the live version the person saw (optimistic concurrency) and treats "already on the target" as a replay. A rollback key column would have needed a migration and adds nothing.
- **No preflight on rollback:** the version passed it when it was published, and rollback is the way out of an emergency. Rules that changed since (for example the form-destination rule becoming blocking in P5) must not trap a freelancer on a broken Live. The version must still parse as a SiteConfig.

## 4. Security review

- **Tenant isolation:** every version id from the browser is only a selector, looked up under RLS inside the selected project; a foreign or unknown id is `NOT_FOUND` everywhere, never `FORBIDDEN` (IDOR harness: 2 new actions, 3 new page/route loaders, new selector `siteVersionId`).
- **Authorization:** rollback is `site.publish` (owners, admins) in the service and the RLS policy underneath; editors and viewers are refused (tested). Restore is `draft.edit` and needs the edit lock. Archived projects refuse both.
- **Integrity:** versions stay immutable (rollback moves a pointer, restore writes the draft); the pointer row lock serialises rollback against a live publish; a stale page cannot overwrite a newer Live (`LIVE_CHANGED`) or a newer draft (`DRAFT_CONFLICT`).
- **Preview:** no script in the response and none allowed by the policy; framed by the dashboard only; `noindex`, `no-store`; sandbox `allow-same-origin` only (same as the editor). Snapshot image URLs are untrusted and filtered to the asset origin.
- **Content in logs and audit:** audit rows hold ids, numbers and kind only. The diff shows at most 80 characters of a value, to members of the workspace only.
