# Phase 3, slice S8b: client approval before Live, automatic review statuses, review notifications

**Status:** built on `feat/p3-s8b-approval-gate`; tests in section 5; **awaiting Owner approval**. **Date:** 2026-11-18 · **Requirements:** FR-PUB-06 (workspace policy "require client approval before Live"), FR-PRJ-02 (lifecycle transitions validated and audited), FR-NOT-01 (in-app and e-mail notifications with preferences) · **ADRs:** 002, 004, 005, 007 · **Modules:** 06, 02, 09 · **Plan approved by the Owner 2026-11-18** ("plan approve hai", recipients as recommended: the project's creator plus owners and admins). **Migration:** `20261118120000_p3_s8b_approval_gate`; the live database needs a separate Owner OK, and it is applied **before** the merge (lesson from S8a, report section 10 there).

## 1. Why

S8a recorded the client's approval but nothing depended on it: an owner could publish to Live whatever the client had or had not seen, the project stayed "Draft" while the client was reviewing it, and nobody was told when the client commented or approved. S8b lets a workspace make the approval binding, keeps the project status in step with the review, and tells the people who need to act.

## 3. Decisions

From the approved plan:

1. **Policy default off**, for existing and new workspaces, so nothing changes for anyone until an owner or admin switches it on.
2. **Exact content:** the gate compares checksums (canonical config + image snapshot). Any edit after the approval needs a new approval; changing the site back to exactly the approved content is approved content again.
3. **No bypass button.** An owner who must publish anyway switches the policy off, which is audited.
4. **Rollback exempt:** putting an earlier Live version back is the way out of an emergency.
5. **Approvals stay valid** when their review link is turned off or expires (an approval is an immutable record, S8a decision 6).
6. **Statuses by the system, audited:** a review link moves only a Draft project; an approval moves only an In review project. A project a member sent back to Draft, or one already Approved/Live, does not move (the approval is still recorded).
7. **Notices:** approval at once; comments at most once per link per 15 minutes; recipients are the project's creator, owners and admins (Owner's choice 2026-11-18), each by their own preferences.

Design choices inside the plan:

- **Database-side notices.** The client acts through the sites app, which has no job client. Writing the notice in the same database transaction as the approval or comment keeps them atomic and needs no new service. The e-mail outbox row is sent by the existing `outbox.sweep` cron, so an e-mail can arrive up to about 6 minutes after the in-app notice (DG-37 (i)).
- **Gate in two places.** The service gives a clear error and the panel explains it before anyone clicks; the trigger makes sure no other code path can write an unapproved Live version.
- **Not changed:** a member's own status buttons (for example "Approve" by an owner) work as before; the policy gates the Live publish, which is what reaches the public. A Live publish does not set the project status to Live (unchanged from S7a).

## 4. Security review

- **Privilege:** the two new helpers are executable by no role (asserted in `db:verify` for `app_public` and `app_user`). The system status move needs both the `svc_definer` identity and the transaction flag; an editor who sets the flag and updates the status is refused with 42501 (integration test). The new `svc_definer` update policy only allows Draft/In review rows to become In review/Approved.
- **Gate integrity:** the trigger runs for every insert of a Live version, as the inserting member, inside RLS. A Live version written past the service with an unapproved checksum is refused with P5105 (integration test).
- **Tenant isolation:** the policy action is registered with the IDOR harness (another workspace's id is refused like every other action); the isolation matrix and IDOR harness pass. Notices are addressed to members of the project's own workspace through the composite foreign key.
- **Personal data:** notice payloads, outbox rows and audit rows hold ids, the version number and reason codes only; the inbox and e-mail never show the client's name, e-mail or comment (asserted). The client's name stays on the feedback tab, as in S8a.
- **Abuse:** a client cannot flood members' inboxes: comment notices are limited to one per link per 15 minutes on top of the S8a limits (30 posts per link per hour, 10 per IP per minute, 300 comments per version).
- **Refusal page:** escaped, no script, review CSP, `no-store`; only the link's own review path is linked.

## 7. Cost

No new service or subscription. Notices are rows in the existing database; e-mails use the existing outbox, Inngest job and capture transport (no e-mail is actually sent until DG-10). Inngest runs one extra job per e-mail notice, well inside the free tier at today's volume.

## 8. Live application (not yet run)

Order, learnt in S8a: Owner approval → separate Owner OK for the live migration → read-only pre-check → `prisma migrate deploy` (`DB_TARGET=env`) → drift check → `db:verify --target env` → `test:live` → **then** merge. The migration only adds a column with a default, triggers, functions, grants, policies and an index; the replaced functions keep their signatures, so the code on production keeps working before the merge. The new Live gate only acts once someone switches the policy on.
