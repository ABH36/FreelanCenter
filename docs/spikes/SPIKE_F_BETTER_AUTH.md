# Spike F - Better Auth on Prisma 7 behind a transaction-mode pooler (DG-05)

**Status: VERIFIED (2026-10-22).** Automated suite 36/36 on 7 fresh-volume runs (one earlier non-fresh re-run showed 4 uncaptured failures, not reproduced - see Limits). **Live Google round trip passed** with a real Google test account.
Code: [spikes/spike-f-better-auth](../../spikes/spike-f-better-auth) · Raw results: `spikes/spike-f-better-auth/results/spike-f-results.json`
Reproduce: `cd spikes/spike-f-better-auth && pnpm spike:up && pnpm spike:generate && pnpm spike:test` (needs Docker).

## Question

ADR-006 chose Better Auth as a working assumption but recorded as unverified: Prisma 7 compatibility, persistence that does not weaken the SRS 5.3 RLS pattern, TOTP, session rotation, and Next 16 integration. Phase 1 Task 0(b) and gap DG-05 require a proof of sign-up, email verification, login, OAuth, TOTP and rotation before auth schema work depends on it.

## Setup (what was actually run)

| Item        | Value                                                                                                                                                                 |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Library     | `better-auth` **1.7.12** (exact pin), `twoFactor` plugin, database rate limiter, `prismaAdapter`                                                                      |
| ORM         | Prisma **7.10.0**, `@prisma/adapter-pg`, multi-schema (`identity`, `public`); `transactionOptions` 20 s/20 s, client pool 10                                          |
| Database    | Postgres 17 (docker `postgres:17-alpine`) through PgBouncer, `pool_mode = transaction`, `pool_size = 2`                                                               |
| Roles       | `app_auth` (identity schema only), `app_user` (tenant tables, RLS), `migrator` (owner). None is superuser or BYPASSRLS                                                |
| Driver path | Every auth call goes through Better Auth's real `Request -> Response` handler (what `toNextJsHandler` mounts in Next 16) with a cookie jar, not through internal APIs |
| TOTP check  | Independent RFC 6238 implementation (`src/totp.ts`), so Better Auth is not verified with itself                                                                       |

### Design under test: identity is separated from tenancy by role, not by RLS

Identity rows (users, sessions, accounts, verification tokens, TOTP secrets, rate-limit counters) are global, so they carry no `workspace_id` and cannot use the workspace policy. Instead they live in schema `identity`, reachable **only** by `app_auth`, the role the auth route uses. The normal tenant role `app_user` has no `USAGE` on that schema. The bridge from a signed-in user to their workspaces is the tenant table `membership`, which gets a second, read-only policy keyed on a transaction-local actor setting:

```text
cookie -> Better Auth (app_auth) -> session.user.id
       -> app_user transaction: set_config('app.user_id', id, true)
       -> membership policy self_read: user_id = current_actor_user()   (SELECT only)
       -> chosen workspace -> set_config('app.workspace_id', ws, true) -> normal RLS
```

`current_actor_user()` uses the same mandatory `NULLIF(..., '')` form as `current_workspace()` (Spike B B-1).

## Findings that change the plan or the product configuration

| ID   | Finding                                                                                                                                                                                                                                                 | Severity | Consequence                                                                                                                                                                                          |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-1  | Better Auth stores verification identifiers (password-reset tokens, OAuth state) **in plain text by default** (`verification.storeIdentifier: "plain"`). That violates FR-AUTH-04/SEC-11 "hashed at rest".                                              | S2       | Mandatory config `verification: { storeIdentifier: 'hashed' }`; result #11 proves it.                                                                                                                |
| F-2  | Better Auth **disables origin/CSRF checks automatically when it detects a test runner** (`skipOriginCheck = isTest()`). The first run of result #20 returned `200` for `Origin: https://evil.example`. Product tests would silently pass with CSRF off. | S2       | Mandatory config `advanced.disableOriginCheck: false`, and a permanent CSRF test in the product suite.                                                                                               |
| F-3  | Session tokens are stored **in plain text** in `identity.sessions` (`sessionTokenAtRest: "plain"`). Anyone who can read that table (or a backup) can hijack sessions. No hashing option exists in 1.7.                                                  | S3       | Accepted with controls: only `app_auth` can read it (result #1); 7-day expiry; "log out all" works; encrypted backups (SEC-14). Revisit if Better Auth adds hashed sessions; record in threat model. |
| F-4  | The email-verification token is a stateless HS256 JWT (1 h), not single-use or revocable. Replay **after** verification mints no session (result #4); before first use, the link is equivalent to a login.                                              | S4       | Keep `expiresIn` at 1 h; note in threat model.                                                                                                                                                       |
| F-5  | The rate limiter keys on the configured IP header. With `x-forwarded-for` trusted blindly, a client can rotate the header to evade limits.                                                                                                              | S2       | Product must set `ipAddressHeaders`/`trustedProxies` to the real edge's trusted header (Vercel) and keep the SEC-19 edge rate limit. Decide in the P1 auth slice.                                    |
| F-6  | Default 2FA lockout is 10 attempts / 15 min; this spike used 5. Default sign-in limit is also generous.                                                                                                                                                 | S4       | Product sets explicit limits (values in `src/auth.ts`).                                                                                                                                              |
| F-7  | Sign-in median latency for an existing account was ~20 ms higher than for an unknown one (176 vs 156 ms). Weak timing oracle.                                                                                                                           | S4       | Mitigated by the per-IP limit; re-measure in P8 load tests.                                                                                                                                          |
| F-8  | Importing the `better-auth/plugins` barrel did not complete within 120 s on this Windows machine; subpath imports (`better-auth/plugins/two-factor`) load in ~5 s.                                                                                      | S4       | Product imports plugin subpaths only.                                                                                                                                                                |
| F-9  | `EMAIL_FROM` in `.env.local` is a `gmail.com` address. Transactional providers (Resend) only send from a verified domain the sender controls.                                                                                                           | S3       | Real email delivery (DG-10) needs a verified sending domain, or the provider's test sender for development. Not a DG-05 blocker: mail is captured by a test sink here.                               |
| F-10 | Google `access_token` and `id_token` were stored **in plain text** in `identity.accounts` (live run). They grant access to the user's Google profile until expiry.                                                                                      | S2       | Mandatory config `account: { encryptOAuthTokens: true }` (XChaCha20-Poly1305 keyed by `BETTER_AUTH_SECRET`); manual script now asserts it.                                                           |

Telemetry is off by default in 1.7 and is pinned off explicitly (`telemetry.enabled: false`) so no undeclared processor appears in the privacy inventory.

## Limits (stated plainly)

- **Google live run (2026-10-22, passed):** a person signed in with a Google test account through `pnpm spike:oauth` (Better Auth's real `/api/auth/callback/google` handler, served on localhost:3000). Callback `200`; Google account linked with `email_verified = true`; scopes exactly `openid`, `userinfo.email`, `userinfo.profile`; audit hooks emitted `auth.user.created` and `auth.session.created`. Evidence (email masked): `results/spike-f-google-oauth.json`. That run used the default token storage and found F-10; after the fix the manual script asserts tokens are not stored in plain text, and a re-run is optional confirmation.
- **Port conflict found while running it:** with `pnpm dev` holding `[::]:3000`, the old script's `127.0.0.1` bind also succeeded and the browser reached the dashboard (404). The script now binds dual-stack and fails with a clear `EADDRINUSE` message.
- **Pooler:** local PgBouncer, not Supabase Supavisor. Spike B already proved the same Prisma adapter path on Supavisor (DG-01); auth adds no new driver behaviour, but a live re-run is cheap if the Owner wants it.
- **One unexplained run:** after the `vite` override reinstall, one re-run against the already-used database reported 32/36. Its failure output was not captured, and the next 5 runs (1 non-fresh, 4 fresh) all passed. It is treated as an open flake: the product auth suite must run repeatedly in CI before this is considered settled.
- **Email delivery:** a capturing sink, not a real provider (see F-9; DG-10 owns delivery).
- **Not in scope:** RBAC matrix, invitations, workspace switcher UI, MFA-required policy for payout/white-label owners (FR-AUTH-03 policy part), admin MFA (SEC-17). These are P1 product slices that build on this proof.

## Recommendation

Accept ADR-006 (Better Auth) **with the mandatory configuration above** (F-1, F-2, F-5, F-6, F-8, F-10) and the `identity`-schema / `app_auth` role split as the persistence pattern. All DG-05 proof items are evidenced; DG-05 closes when the Owner ratifies ADR-006.
