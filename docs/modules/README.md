# Module Delivery Documentation

## Purpose

This directory is the implementation companion to the frozen `SRS.md`. It is designed for humans and AI implementation agents working module by module without losing cross-module contracts.

## Authority and truthfulness

1. `SRS.md` is the product-requirement source of truth. `DEVELOPMENT_PLAN.md` is its generated byte-identical mirror.
2. An ADR is required before changing a requirement or a material architecture decision.
3. A requirement is **Planned** until code, automated tests, review evidence, and a phase report prove it is implemented. Documentation must never label SRS requirements as implemented merely because they are specified.
4. Current repository status is **Phase 0 complete with conditions; no product feature is implemented**. See `docs/reports/PHASE_0_AUDIT.md`.
5. Existing `docs/enterprise-enhancements/` is an untracked exploratory proposal set. It may be used for ideas but is not authoritative and must be reconciled with the SRS before adoption.

## How to use a module document

Before implementation, an agent must read: this file, the target module file, every linked SRS requirement/ADR, and its upstream module contracts. It then implements only the stated slice, records deviations in an ADR, and proves the acceptance criteria with automated evidence.

Read `docs/governance/DOCUMENTATION_INDEX.md` first for the mandatory task-specific reading matrix, and `docs/governance/DOCUMENTATION_GAP_REGISTER.md` before any phase/vendor-dependent work. Shared rules are in `docs/governance/CROSS_MODULE_CONTRACTS.md`; all agents must follow root `AGENTS.md`.

Every module document includes: scope, contracts, state/data, flows, security, failure handling, dependencies, test evidence, rollout/rollback, and an AI handoff checklist.

## Non-negotiable cross-module invariants

- Tenant-owned rows carry `workspace_id`; access occurs through the transaction-scoped RLS pattern in SRS §5.3.
- All externally retried mutations are idempotent; state transitions are validated server-side and audit logged.
- Site drafts are mutable; published `SiteVersion` objects are immutable; live traffic resolves only an approved immutable version.
- Template definitions are declarative in v1: no arbitrary creator React/JavaScript.
- AI output is an untrusted proposal: validate, preview, then explicitly accept before persistence.
- Entitlements, permissions, template licences and export rights are enforced on the server, never only in UI.
- Secrets are envelope-encrypted, never returned after write and never logged.
- No implementation may silently broaden scope. Record a question or ADR instead.
